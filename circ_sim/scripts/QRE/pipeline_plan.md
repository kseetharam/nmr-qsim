# Fault-tolerant resource estimation pipeline: planning notes

## Goal

Flesh out a (fault-tolerant, platform-agnostic) quantum resource estimation
pipeline for estimating **local observables** (e.g. gyromagnetic-weighted
total magnetization / the `coil` operator) after time-evolving an initial
state under an **in-solution NMR Hamiltonian** -- the coherent (Heisenberg +
Zeeman) + dissipative (Lindbladian jump-operator) systems developed in
`circ_sim/scripts/QRE/notes/qre.tex` and generated by the
`circ_sim/scripts/{fluo_suite,gemcitabine_trunc,linblad_dyn}` pipeline.

## Design constraints

- **Modular in the pulse sequence.** Different NMR pulse sequences (state
  preparation, pulses, delays, detection) must be pluggable inputs to the
  pipeline, not hardcoded, so that resource-estimating a new experiment is a
  matter of swapping this one piece rather than rebuilding the pipeline.
- **Platform-agnostic for now.** Stay at the algorithmic-gadget level:
  costs expressed in terms of abstract primitives (Hamiltonian-simulation
  queries, Trotter steps, block-encodings, ancilla counts, ...), deliberately
  *without* compiling down to a specific QEC code, physical error rates, or
  logical-to-physical qubit overhead. Platform-specific compilation is an
  explicit non-goal for this phase.

## Relationship to existing work

- `notes/qre.tex` -- the error-bound derivations (prf vs.\ trot, observable-
  aware/locality-weighted bounds) that this pipeline's error-budget layer
  should consume, plus the numerically-verified scaling on the truncated
  Gemcitabine model.
- `circ_sim/scripts/{fluo_suite,gemcitabine_trunc,linblad_dyn}` -- generates
  the physical inputs (coherent Hamiltonian $H_0$, canonical jump operators
  $L_j$, ZULF protocol operators) this pipeline consumes as data, for a given
  molecule/spin-system.

## Pipeline architecture (draft skeleton -- to refine together)

1. **Input specification layer.** Spin system (Hamiltonian + jump operators,
   as already produced upstream), pulse sequence, target observable, target
   precision / failure probability.
2. **Algorithmic primitive layer.** State preparation, Lindbladian
   simulation gadget (dilation + Trotterization, per `qre.tex`), observable
   estimation gadget.
3. **Error budget composition layer.** How per-gadget errors (prf, trot,
   state prep, observable estimation) combine into a total error budget for
   a target precision.
4. **Resource counting layer.** Gate/ancilla/query counts as a function of
   the above, still platform-agnostic.
5. **(Explicitly out of scope for now) Platform-specific compilation
   layer.** QEC code, physical error rates, logical-to-physical overhead.

## Status: first complete baseline estimate (2026-09-22)

Every gadget layers 1-4 need now exists, is independently verified, and has
been assembled into one end-to-end circuit/resource total for truncated
Gemcitabine (`full_pipeline_estimate.py`): state prep
(`state_prep.build_null_state_prep`) -> $M$ x (coherent step
(`coherent_trotter_step.build_coherent_trotter_step`) + nested/dispatch
step (`nested_trotter_step.build_nested_trotter_step`)) -> readout
(`coil_readout.build_coil_readout`, X- and Y-basis variants). $M\sim2\times
10^4$ makes building the literal $M$-step circuit as one Qualtran
`CompositeBloq` intractable, so the total is computed as $M\times$(one
step's measured cost) + one-time pieces -- but that linearity is *checked*,
not assumed: a literal $M_{\text{test}}=1,2,3$-step chain is built and its
`QECGatesCost` confirmed to scale exactly linearly (and its `QubitCount`
confirmed constant, i.e.\ the unary-iteration dispatch's transient flag
ancilla are reused across steps, not accumulated) before trusting the
extrapolation.

At $\varepsilon_{\text{total}}=0.1$, $t=1\,$s (this pipeline's running
example throughout), optimal split $v^\ast\approx0.967$: $\Dt^\ast\approx
9.34\times10^{-5}\,$s, $M=10{,}711$ steps, $\varepsilon_{\text{gate}}
\approx1.17\times10^{-10}$ (48 T/rotation). **Per full circuit run
(either X- or Y-readout variant, essentially identical since readout
itself costs 0 T): $\approx1.36\times10^9$ T-gates, $\approx1.14\times
10^8$ Clifford gates, $28{,}223{,}488$ rotations, $321{,}330$ `And` gates,
$321{,}335$ measurements, 14 peak qubits** ($5$ system + $5$ dispatch-
select + $4$ transient flag ancilla). Reconstructing $\langle\text{coil}
\rangle$ needs *both* variants run as separate circuit executions (not
summed) -- see `full_pipeline_estimate.py`'s module docstring.

This is the pipeline's first genuine complete baseline number, not a final
validated resource estimate: every caveat already logged below still
applies verbatim -- ZULF-branch only ($K_{\text{nested}}\approx0$
assumed), null state prep (not a validated $\rho_0$ substitute, no
$t$-design refinement), single-shot cost only (the shot-count multiplier
needed to converge $\langle S_x^{\text{coll}}\rangle$/$\langle
S_y^{\text{coll}}\rangle$ to a target precision is still out of scope, per
the Decision log), and Gemcitabine-specific (the mechanism generalizes,
per open question 6, but a concrete second molecule hasn't been run
through this same assembly).

   Pauli terms $\text{coil}=\sum_nw_nS_n^+=S_x^{\text{coll}}+i\,S_y^{\text{coll}}$
   with $S_x^{\text{coll}}=\tfrac12\sum_nw_nX_n$,

   sums -- estimate each directly (X-/Y-basis) and combine classically as
   $\langle\text{coil}\rangle=\langle S_x^{\text{coll}}\rangle+i\langle

   Hermitian $S_x^{\text{coll}}$ read-out entirely (i.e.\ not tracking
   $S_y^{\text{coll}}$ at all) -- unlike the high-field rotating-frame case,
   ZULF has no carrier/down-conversion, and the $\pm J$ singlet-triplet
   transitions this protocol's unequal spin weights are specifically
   designed to excite are not sign-definite; discarding the imaginary
   channel would symmetrize $+J$ and $-J$ together and destroy the sign of
   the $J$-coupling, a genuine ZULF observable, not a redundant mirror.

   however many Trotter steps, rotation count could be large. Whether to use
   direct rotation synthesis or phase-gradient synthesis, and whether to

   swappable abstraction; the nested-Trotter mitigation choice was the
   other still-open part of this item, resolved the same day -- see
   below). Every Pauli-string
   exponential in this pipeline reduces to a Clifford CNOT ladder wrapping
   one Rz, so the whole gate-synthesis cost model lives in how that one Rz
   is synthesized. **Decision: direct synthesis (`qualtran.bloqs.basic_gates.Rz`)
   is the baseline**, not phase-gradient -- checked empirically rather than
   assumed: a fully-wired Qualtran circuit of $N=20$ rotations at
   $\varepsilon=10^{-8}$ costs $220$ T directly synthesized vs. $2538$ T via

   (or comparing) cheap later, added `rotation_synthesis_strategy.py`:
   a `RotationSynthesisStrategy` interface (`DirectSynthesisStrategy`,
   `PhaseGradientStrategy`, both implemented and working) that Trotter-
   circuit-building code should be written against, mirroring the
   `ErrorAccumulationModel` pattern -- so trying phase-gradient again later
   is swapping a strategy object, not rewriting the circuit.

   not the higher-order (Strang) inner splitting, for baseline resource
   estimates.** Reasoning: grouping only prunes *which pairs* contribute to
   the existing first-order error formulas (`qre.tex` Eqs.
   `nested_trot_final`, `Mpj_pair`) without changing the gate-counting model
   itself; the higher-order splitting would change the gate-counting model
   itself (a 4th-order Suzuki formula's standard $5\times$ recursive gate
   overhead per level), a bigger, separate change better deferred past a
   first baseline. Added
   `nested_trotter_grouping.py`: partitions a jump operator's Pauli terms
   into groups of pairwise-compatible (commuting *and* matching-phase-mod-
   $\pi$) terms via greedy conflict-graph coloring, fusable into one exact
   exponential (zero Trotter error within a group). Corrected `qre.tex`'s
   stated compatibility condition along the way: $\Xi_j(\phi)$,
   $\Xi_j(\phi')$ commute whenever $\phi\equiv\phi'\pmod\pi$ (not just at
   exact equality -- at $\phi'=\phi+\pi$, $\Xi_j(\phi')=-\Xi_j(\phi)$
   exactly, verified). Applies to the nested-Trotter bound, $\calC_j^{(3)}$,

   transform the resource picture for this system; logged as measured,
   not assumed.

9. **Is the 50/50 Trotter/synthesis split from item 8 actually optimal?**
   **Resolved 2026-09-21.** No -- co-optimized $\Dt$ against total T-count
   instead of using a fixed split, same spirit as the earlier prf/trot
   co-optimization (open question 2). Since $T_{\text{total}}(\Dt)$ scales
   *linearly* in the Trotter step count $M=t/\Dt$ but only
   *logarithmically* in the per-gate synthesis precision
   $\varepsilon_{\text{gate}}$, the optimal split is strongly asymmetric:
   for the Gemcitabine baseline ($\varepsilon=0.1$, $t=1$s, $R=1110$
   rotations/step), the optimal fraction of the budget spent on Trotter
   error is $v^\ast\approx0.966$ (vs.\ $0.5$ at baseline), cutting total
   T-count from $9.89\times10^8$ to $5.47\times10^8$ -- a $1.81\times$
   reduction, for free (same $\varepsilon$, same circuit, just a better
   $\Dt$). Derived a transcendental stationarity equation for $v^\ast$
   (`qre.tex` Sec.~\ref{sec:optimal_split}, Eq.~\eqref{eq:optimal_split_transcendental});
   solved two independent ways (direct numerical minimization over $\Dt$,
   and root-finding on the transcendental equation itself) that agree to
   4+ decimal places, and cross-checked the continuous-approximation
   optimum against the exact discrete (ceiling-inclusive) T-count formula
   -- the $\approx1.8\times$ improvement survives, confirming it isn't an
   artifact of the smooth approximation. Scanned the asymmetry across
   $10^3$--$10^{12}$ in the problem-size parameter $B=tRa/\varepsilon^2$:
   the synthesis-budget share $1-v^\ast$ shrinks only *logarithmically*
   with $B$, so this qualitative asymmetry (favor Trotter-error budget,
   spend only a small tail on synthesis) should generalize well beyond the
   specific Gemcitabine numbers. Implemented in
   `optimal_error_budget_split.py`. Restricted, like item 8, to the ZULF
   branch ($K_{\text{nested}}\approx0$); the off-ZULF extension is
   structurally straightforward (shifts the usable budget by the constant
   floor $t|K_{\text{nested}}|$) but not yet implemented. `gate_synthesis_budget.py`'s
   50/50 split still stands as the *default* in that module -- callers
   that want the optimal split should call
   `optimal_error_budget_split.optimal_split()` explicitly for now; folding
   it in as `gate_synthesis_budget.py`'s new default is a natural but
   not-yet-made follow-up change.
10. **Jump-operator ancilla dispatch: local (one-hot, one qubit per jump
    operator) vs.\ non-local (compact log-register + SELECT)?**
    **Resolved 2026-09-21.** Non-local wins decisively, but only once
    dispatched via *unary iteration* rather than a naive per-rotation
    multi-controlled SELECT -- naive non-local would have paid its dispatch
    cost once per Pauli-term rotation (multiplicative in $\sum_jP_j$), which
    is what made local look attractive in the first place. Unary iteration
    (`qre.tex` Sec.~\ref{sec:unary_iteration}, added this week specifically
    to resolve this question, with literature refs and a worked $L=4$
    example) pays dispatch once per Trotter step (additive in $L$, not
    $\sum_jP_j$), via a segment-tree walk with `And`/`And^\dagger` gates.
    Built and directly compared both schemes on Gemcitabine's real 25 jump
    operators (`jump_dispatch_comparison.py`): **local costs 30 qubits
    ($25+5$) for 0 dispatch gates; non-local costs 14 qubits ($5+5+4$) for a
    120-T, 30-measurement dispatch overhead ($0.15\%$ of the payload's
    79,200 T) -- 16 fewer qubits at negligible gate cost.** Verified the
    payload compilation is identical between schemes (both give exactly
    1800 rotations), isolating the comparison to dispatch alone: local uses
    the physical one-hot ancilla directly as the hop rotation's "ancilla
    role" qubit; non-local uses the unary-iteration walk's own flag qubit
    the same way, with zero extra controlling (built directly with
    `qualtran.bloqs.mcmt.and_bloq.And` in a new `unary_iteration.py`,
    *not* `ApplyLthBloq` -- the latter's generic controlled-bloq wrapping
    of each leaf turns every CNOT of the leaf's own basis-change/CNOT-ladder
    into a Toffoli and every Clifford basis-change into a $T$-costly
    controlled gate, empirically $\sim7000$ spurious Toffolis and $14\times$
    too many rotation-costed bloqs -- a real trap, not just a theoretical
    concern). Also corrected: vacuum needs no dedicated qubit in *either*
    scheme (a $\ge0$-excitation one-hot register over $S_k=25$ qubits
    already covers all $26$ ancilla-register states including vacuum), so
    local costs $S_k=25$ qubits and the SELECT range is $L=S_k=25$, not
    $26$ -- a minor correction to `qre.tex`'s own pedagogical $L=26$
    worked example.
    **Genuine implementation bug caught along the way** (documented in
    `unary_iteration.py`'s docstring and `qre.tex`): the uncomputing `And`
    must use `cv2=1-`(compute `cv2`), not the same `cv` as the computing
    `And` -- the intervening CNOT changes which boolean combination the
    flag equals, so reusing the compute step's `cv` for uncompute silently
    produces a non-unitary, all-zero circuit (caught by tensor-contracting
    a trivial identity-payload tree and finding it wasn't the identity;
    cross-checked against `ApplyLthBloq`'s own decomposition, which uses
    exactly `cv=(1,1)`/`cv=(1,0)`).
    **Correction surfaced by actually building the payload, propagated
    2026-09-22**: `gate_synthesis_budget.count_rotations_per_step`'s
    $R_{\text{nested}}=1075$ (raw Pauli-term count) undercounted the true
    rotation count -- a hop term needs a second rotation whenever *both*
    $\text{Re}(c_{j,n})$ and $\text{Im}(c_{j,n})$ are nonzero (true for 860
    of 1075 terms), giving **1800 actual rotations, a 67% increase**,
    verified by both dispatch schemes independently agreeing. Fixed by
    moving `jump_dispatch_comparison.py`'s `hop_pieces`/
    `count_hop_rotations` into `gate_synthesis_budget.py` (the module that
    owns rotation counting) and having `count_rotations_per_step` call
    `count_hop_rotations` for $R_{\text{nested}}$ instead of the raw term
    count; `jump_dispatch_comparison.py` now imports them back, so the two
    modules share one rotation-counting implementation instead of it
    silently drifting. Propagated through `optimal_error_budget_split.py`
    and `qre.tex` Secs.~\ref{sec:dt_solver}--\ref{sec:optimal_split}: for
    Gemcitabine, $R=35+1800=1835$ (not $1110$). $\Dt^\ast$/$M$ are
    essentially unchanged (they depend on $R$ only through $v^\ast$, which
    itself depends on $R$ only logarithmically: $v^\ast=0.9667$ vs. the old
    $0.9661$); absolute T-counts scale up by $\approx1.65\times$
    ($R_{\text{new}}/R_{\text{old}}$) to $1.64\times10^9\to9.14\times10^8$
    T (continuous, 50/50$\to$optimal split) and
    $1.67\times10^9\to9.24\times10^8$ T (discrete) -- the $\approx1.8\times$
    split-optimization improvement itself is unaffected, only the absolute
    totals. Verified `jump_dispatch_comparison.py` still reproduces the
    same 1800/79,200/79,320-T numbers after the refactor (no regression).
    **A second, more serious correctness bug caught the same day while
    promoting the winning non-local scheme into a reusable gadget** (the
    natural next step after this comparison script, per the plan below).
    That "1800" fix itself turned out to be wrong, not just imprecise: it
    compiled each hop term's coefficient $c_{j,n}$ into up to *two
    independent, sequential* rotations (one on $X_a\otimes P$, one on
    $Y_a\otimes P$) whenever both $\text{Re}(c_{j,n})$ and
    $\text{Im}(c_{j,n})$ were nonzero. But `qre.tex`'s own derivation
    (Sec. `Vj_block_encoding`) treats each hop term as *one atomic
    exponential* of a single combined generator
    $\Xi_j(\phi_{j,n})\otimes P_{j,n}$ — and $X_a\otimes P$,
    $Y_a\otimes P$ *anticommute*, so the two-piece sequential product
    disagrees with the true exponential at $O(\Delta t)$ per affected term
    (a short BCH expansion) — the same order as $K_{\text{nested}}$, whose
    vanishing at ZULF field is the entire basis for the pipeline's clean
    $O(\Delta t^2)$ scaling, and whose cancellation this new discrepancy
    was never checked to share. Not caught by gate-counting (both
    compilations report *a* T-count) — caught by re-deriving the
    compilation against `qre.tex`'s own math while writing the reusable
    version, rather than trusting the already-"verified" comparison
    script. **Exact fix**: $\Xi_j(\phi)=\cos\phi X-\sin\phi Y$ is a
    Z-conjugated $X$ ($\Xi_j(\phi)=R_z(-\phi)\,X\,R_z(\phi)$, a standard
    single-qubit identity), so the atomic exponential is realized exactly
    as $R_z(\phi)\to$ [single $X\otimes P$ rotation] $\to R_z(-\phi)$ — 1
    rotation when the term is purely real or purely imaginary (no
    conjugation needed, $\phi$ a multiple of $\pi/2$), 3 otherwise (2
    conjugation $R_z$'s + 1 payload rotation). Gives the *true* count
    $R_{\text{nested}}=\mathbf{2600}$ for Gemcitabine ($800$ terms need 3
    rotations, $200$ need 1, $75$ are negligible — verified by direct
    tabulation, not the earlier docstring's approximate "860 of 1075"
    figure), vs. $1800$ (flawed two-piece) and $1075$ (raw term count).
    Verified two ways: the conjugation identity itself against a direct
    `numpy` matrix exponential (agreement to $2\times10^{-16}$), and the
    resulting rotation count against `gate_synthesis_budget`'s independent
    tally (exact match). Implemented in new module
    `nested_trotter_step.py`: `apply_hop_term` (the exact per-term
    compilation) and `build_nested_trotter_step` (the full reusable
    non-local/unary-iteration gadget promoted out of
    `jump_dispatch_comparison.py`'s `build_nonlocal_dispatch`, mirroring
    `coherent_trotter_step.build_coherent_trotter_step`'s interface).
    `jump_dispatch_comparison.py`'s non-local branch now just calls
    `build_nested_trotter_step` directly (no duplicated payload logic);
    re-ran it and confirmed local/non-local still agree with each other
    (2600 rotations both, dispatch overhead still exactly 120 T — the fix
    only touched payload compilation, not dispatch) and the non-local
    scheme still wins on qubit count. Propagated (again) through
    `gate_synthesis_budget.py`, `optimal_error_budget_split.py`, and
    `qre.tex`: for Gemcitabine, $R=35+2600=2635$, $v^\ast=0.9671$
    (essentially unchanged from $0.9661$ pre-correction, since $v^\ast$
    depends on $R$ only logarithmically), $\Dt^\ast\approx9.34\times10^{-5}$s
    (essentially unchanged), total T-count $2.39\times10^9\to1.33\times10^9$
    (continuous, $50/50\to$optimal, $1.79\times$) and
    $2.40\times10^9\to1.35\times10^9$ (discrete, $1.77\times$) — absolute
    totals now $\approx2.4\times$ the original uncorrected estimate, but
    the split-optimization benefit itself is unaffected. Open question 7's
    `RotationSynthesisStrategy` abstraction and open question 9's optimal
    split both survive this unchanged (both operate on $R$ as an opaque
    count, indifferent to how it's derived).

## Decision log

- **Pulse sequences enter the pipeline as unitaries interspersed with free
  Lindbladian evolution segments.** A pulse sequence is a sequence of
  (instantaneous unitary, free-evolution-duration) pairs, not a
  time-dependent modification of $H_0(t)$ and not just a choice of $\rho_0$.
- **Shot noise / observable-estimation statistics are out of scope for now.**
  The pipeline targets the quantum resources needed for a *single circuit
  shot* (one run of state prep + evolution + readout); how many shots are
  needed to beat down sampling noise is deferred. **Scope expanded
  2026-09-18**: this now also covers the state-preparation trajectory count
  (see the state-preparation decision below) -- both the number of
  measurement shots *and* the number of initial-state trajectory samples
  needed for a target precision $\varepsilon$ on $\langle\hat O\rangle$ are
  deferred to the same future shot-budget analysis. Until then, resource
  estimates report the cost of a single trajectory's single shot, with the
  combined sampling-overhead multiplier left as an explicit placeholder.
- **State preparation for $\rho_0$: trajectory-like (pure-state ensemble)
  sampling, not a single mixed-state-preparation circuit.** $\rho_0$ (the
  ZULF sudden-transfer + $\pi/2$-pulse high-temperature deviation density
  matrix) is not a proper pure state and has no natural single-circuit
  preparation the way a product or ground state would. Chosen approach:
  sample initial *pure* states from an ensemble that reproduces $\rho_0$'s
  expectation values, emulate the full protocol (state prep + evolution +
  readout) per sampled pure state, and average the observable estimate
  classically over samples -- the same spirit as quantum-trajectory
  unravelings of a mixed initial state, rather than a mixed-state-prep
  circuit. The exact unraveling/sampling scheme for this specific $\rho_0$
  (which is a traceless high-temperature *deviation* operator, not
  itself a valid density matrix) is a placeholder for future refinement,
  as is its interaction with the shot-budget analysis above.
  **Superseded for baseline resource estimates, 2026-09-21: state prep is
  null.** Building the trajectory/ensemble-sampling machinery above is
  deferred; for now, treat the "sudden transfer" step as free (register
  starts at $\ket{0\cdots0}$, as Qualtran registers already do) and apply
  the real $y$-pulse circuit directly to that, rather than to $\rho_0$'s
  physical precursor $\rho_{\text{sud}}=\sum_nw_nS_{n,z}$. This is *not*
  claimed to reproduce $\rho_0$'s actual statistics: $\rho_0$ is a pure
  **sum** of weight-1 deviation terms (by construction, from a genuine
  small-polarization high-temperature expansion), whereas a pure product
  state's density matrix is a **product**, so it unavoidably carries
  weight-2-and-up cross terms $\rho_0$ does not have -- exactly the gap a
  future **approximate state $t$-design** step (appended after this null
  prep, per the original plan for this open question) is intended to
  close, by turning the trivial product state into a better statistical
  stand-in for $\rho_0$ without needing to simulate the true mixed-state
  preparation directly. Until that piece is built, this null-prep baseline
  is a placeholder chosen for concreteness (it gives an actual, costed
  circuit today), not a validated substitute for $\rho_0$ -- in particular,
  the $\rho_0$-anchored $K_{\text{prf}}$/$K_{\text{mixed}}$ coefficients
  (Sec.~\ref{sec:dt_solver}) still describe error accumulation *for the
  real $\rho_0$*, not for this substitute state; whether they remain a
  reasonable proxy for the substitute state has not been checked.
  Implemented and verified in `state_prep.py`.
- **Jump-operator dilation ancilla register: logarithmic-size (SELECT-
  addressed) baseline.** For the single-shot resource-estimate baseline,
  the $D_{\text{anc}}$-level dilation ancilla (one level per canonical jump
  operator plus vacuum -- $26$ levels for Gemcitabine's $25$ active jump
  operators) is encoded in $\lceil\log_2D_{\text{anc}}\rceil$ qubits with a
  SELECT-style addressed register, not one qubit per level. This is a
  working baseline, not a final answer: aggressive truncation of the
  jump-operator set (e.g.\ via the $\ell_1$-norm-based dissipation-channel
  ranking already used for the fluo\_suite systems,
  `dissipation_channel_localization.py`) may show that only a handful of
  jump operators dominate the observable's dynamics, shrinking
  $D_{\text{anc}}$ well below the canonical count -- but that is a
  separate, not-yet-quantified refinement. The jump-operator gadget itself
  (Trotterized $V_j$ Pauli terms, `qre.tex` sec:nested\_trot\_leading) is
  designed around this logarithmic-size register regardless of exactly how
  many levels $D_{\text{anc}}$ ends up needing.
- **"Local observable" is whatever the user precisely specifies** for a
  given resource-estimation run -- not restricted in advance to weight-1
  gyromagnetic-weighted sums (that was just the running example so far).
- **Error metric: absolute error in the observable**, not relative. (Note:
  this differs from the truncated-Gemcitabine numerical demo in `qre.tex`,
  which plotted *relative* error at the time -- worth keeping in mind if/when
  that demo's conventions get reused here.)
- **The prf/trot error budget is co-optimized**, not split by a fixed ratio,
  given their different scaling behavior with $\Dt$ (per the `qre.tex`
  analysis: prf reaches its asymptotic $\Dt^2$ regime much faster than trot
  does for comparable step sizes).
  **Superseded:** prf and the corrected combined trot error are both
  $O(\Dt^2)$ at ZULF/axial field (see the nested-Trotter entry below), so
  there is no longer a two-timescale trade-off to make -- "co-optimization"
  reduces to solving one equation for $\Dt$. See `notes/qre.tex` Sec.
  \ref{sec:dt_solver} and `error_budget_solver.py` (open question 2, now
  resolved).
- **Pulse sequences are interfaced as Python classes.**
- **Framework: build directly on Qualtran (not pyLIQTR).** pyLIQTR is
  itself built on top of Qualtran (its resource estimator extends
  `qualtran.t_complexity`), and is specialized toward QSP/QSVT-based
  simulation of pre-classified Hamiltonians (chemistry, Hubbard, Heisenberg)
  via its `ProblemInstances`/`BlockEncodings` scaffolding -- a narrower fit
  than our bespoke algorithm (ancilla-dilation Lindbladian simulation +
  first-order Trotter, per `qre.tex`). Qualtran's `Bloq`/composite-bloq
  (DAG) abstraction is both more general-purpose for a custom gadget and
  maps directly onto the pulse-sequence decision above (each pulse and each
  free-evolution segment as a bloq, composed into one DAG with automatic
  resource aggregation); going direct also avoids stacking two
  experimental-status libraries. pyLIQTR's `ProblemInstances`/examples
  remain a useful reference if a QSP/qubitization-based treatment of the
  coherent part $H_0$ is explored later.
- **Jump-operator gadget: relegate block-encoding/qubitization; Trotterize
  each $V_j$'s own Pauli terms instead.** Chosen for physical
  transparency/implementation simplicity over the block-encoding route
  (`qre.tex` Sec.~\ref{sec:Vj_block_encoding}). Consequence: this adds a
  *third* error source (nested Trotter error from approximating
  $e^{-i\sqrt{\Dt}V_j}$ by a product over its own Pauli terms), on top of
  prf and trot.
- **Nested-Trotter error derived (`qre.tex` Sec.~\ref{sec:nested_trot_leading}):
  originally found to scale as $O(\Dt)$, one power of $\Dt$ *worse* than
  prf/trot's $O(\Dt^2)$.** Root cause: this inner decomposition's elementary
  parameter is $\sqrt{\Dt}$ (the strength jump operators already enter at,
  per prf), not $\Dt$, so its leading BCH error is $O((\sqrt{\Dt})^2)=O(\Dt)$.
  Two partial mitigations identified but not built in: grouping Pauli terms
  that share *both* commuting support and matching phase, or a higher-order
  (Strang/4th-order Suzuki) inner product formula.
  **Superseded:** this $O(\Dt)$ coefficient ($K_{\text{nested}}$) was later
  shown to vanish via a Pauli-weight-orthogonality mechanism tied to the
  dipolar/CSA ladder-operator structure of the jump operators -- exact at
  zero field, conditional at nonzero field (breaks down for tilted $\mathbf
  B$; see open question 4 above). Treating trot and nested as separately-
  analyzed, additively-combined error sources was itself found to undercount:
  combining both Trotter layers reveals a genuine cross term, and the
  *corrected* combined leading order is $O(\Dt^2)$, not $O(\Dt)$ or the
  naive-per-layer $O(\Dt^3)$ (`qre.tex` Sec.~\ref{sec:combined_trot_nested},
  numerically confirmed via \texttt{check\_combined\_trotter\_scaling.py}).
  The nested-Trotter mitigations above are still relevant if operating at a
  general/tilted field where $K_{\text{nested}}$ does not vanish, but are no
  longer the binding concern at ZULF/axial field.
